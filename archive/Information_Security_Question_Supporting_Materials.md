## Chapter 1: Preface

Introduces Software Security Development Lifecycle \(SDL\) \- integrating security into every development phase: requirements, design, coding, testing, and maintenance\.

## Chapter 2: Security Coding Principles

### 2\.1 Pre\-Launch General Security Development Requirements \(Items 1\-10\)

Overview: Foundational security requirements that must be met before any code deployment\. Focuses on eliminating common attack vectors through proper dependency management, secure configuration, and removing unnecessary exposure points\.

Key Requirements:

- Keep frameworks and third\-party components updated \(especially log4j vulnerabilities\)

- Remove all test content, comments, debug code, SVN/Git files, and backup files before production

- Prohibit high\-risk components: phpMyAdmin, Struts 1/2, Fastjson

- Block external access to: Actuator, nacos, dubbo, minio, kibana, zabbix, spark, hadoop, SSH, FTP, telnet, swagger

- Enforce strong passwords: 8\+ characters with mixed case, numbers, special characters; no default credentials

- For client\-deployed apps \(mobile\): implement code obfuscation, signing, and hardening

### 2\.2 Input Validation \(Items 11\-16\)

Overview: All user input is untrusted and must be validated server\-side\. This is the primary defense against injection attacks\.

Core Requirements:

- Server\-side validation only \- frontend validation can be bypassed

- Whitelist approach \- define what IS allowed, not what isn't

- Filter dangerous characters: `<>'"%|;&/\` for SQL, XSS, command injection

- Framework\-level implementation \- ensure consistency across all endpoints

- Validate internal service data \- even internal sources may pass malicious input

### 2\.3 Authentication and Session Management \(Items 17\-23\)

Overview: Secure practices for user authentication and session handling to prevent session hijacking and unauthorized access\.

Key Requirements:

- Cookie security: Set HttpOnly \(prevent JavaScript access\) and Secure \(HTTPS only\) attributes

- Session timeout: ≤30 minutes for public systems; immediately clear on logout

- Re\-authenticate before critical operations \(payments, password changes\)

- Session\-based identity: Get userid, roleid from session—NEVER from user input parameters

- No session IDs in URLs \- use cookies only

### 2\.4 Registration/Login/Forgot Password \(Items 24\-34\)

Overview: Security requirements for authentication flows to prevent enumeration, brute force, and unauthorized access\.

**2\.4\.1 Self\-Implementation Security:**

- Management platforms: No self\-registration allowed

- B2B systems: Require approval workflow for registrations

- Identity verification: Use SMS/email codes for registration

- Password requirements: 8\+ chars with complexity \(mixed case, numbers, special chars\)

- Generic error messages: "Username or password incorrect" \(prevent enumeration\)

- CAPTCHA lifecycle: Expire immediately after one use

- Audit logging: Log all successful logins \(username, IP, timestamp\)

- Anomaly detection: Multi\-factor auth for unusual login locations

- Rate limiting:

    - IP\-based: 5 attempts in 5 seconds → 30\-min block

    - Account\-based: 3 failures → lock for 30 min OR show CAPTCHA

**2\.4\.2 Login State Isolation:**

- Requirement: Sensitive business systems must use isolated login credentials per business domain

- Implementation: Use company unified login platform to issue business\-specific tokens

### 2\.5 Access Control \(Items 35\-42\)

Overview: Enforce authorization checks, prevent privilege escalation, and ensure proper data isolation\.

Key Requirements:

- No guest accounts: Don't use pre\-embedded accounts for anonymous browsing

- Data minimization: API responses return only necessary fields

- Rate limiting: Enforce login attempt limits \(see 2\.4\.1\)

- Least privilege: New users get minimum required permissions only

- SMS anti\-abuse: 1 code per minute; use locking to prevent SMS bombing

- Query validation: Reject empty parameters that could return all data

- Authorization checks: Validate user ownership of resources to prevent horizontal/vertical privilege escalation

- Sensitive data access: Require explicit authorization for PII, security configs, protected resources

### 2\.6 Transmission Security and Encryption \(Items 43\-45\)

Overview: Secure data transmission and use modern cryptographic standards\.

Requirements:

- POST for mutations: All create/update/delete operations use POST, not GET

- HTTPS everywhere: TLS 1\.2\+ required for all web traffic

- Algorithm standards:

    - Symmetric: AES\-128\+ \(recommended\), RC5/RC6 \(acceptable\)

    - Asymmetric: RSA\-2048\+, DSA\-2048\+, ECC\-256\+

    - Hashing: SHA\-256\+, SHA\-3 \(recommended\); avoid MD5, SHA\-1

### 2\.7 Data Protection \(Items 46\-49\)

Overview: Protect sensitive data at rest, in transit, and during display\.

Requirements:

- Never store in client\-side: No passwords, keys, tokens, internal IPs in JavaScript/localStorage

- Encrypt sensitive data: Database encryption for PII; display with masking \(e\.g\., `****1234` for cards\)

- Random IDs required: No sequential numbers for userid/orderid/couponid 

    - User IDs: 16\+ random characters

    - Order IDs: 32\+ random characters

    - Use SecureRandom or UUIDs

- API rate limiting: Limit requests on sensitive data endpoints to prevent scraping

### 2\.8 File Upload/Download \(Items 50\-62\)

Overview: Multi\-layered security for file operations to prevent malicious uploads and unauthorized access\.

Upload Security:

- Verify identity before accepting uploads

- Whitelist file types by MIME type and extension

- Validate file content: Check magic bytes match declared type; enforce size limits

- Zip bomb protection: Limit decompressed file count and total size before extraction

- Secure storage: Never save in web containers; use dedicated file servers or cloud storage

- Rename files: Use secure random names \(16\+ chars\): `{timestamp}_{random}.{ext}`

- Path traversal prevention: Filter `../` and `..\` from filenames

- No direct OSS uploads: Proxy through backend; never expose credentials to client

Download Security:

- No absolute paths: Don't return filesystem paths to users

- Validate access: Verify file path within allowed directory; check user permissions

- Close streams: Properly close FileInputStream, FileOutputStream, FileReader, FileWriter

### 2\.9 Payment Logic \(Item 63\)

Overview: Critical validations for payment interfaces to prevent financial fraud and business logic exploitation\.

Server\-side validations required:

- Amount protection: Recalculate server\-side; never trust client amounts

- Status protection: Payment status only updated by verified gateway callbacks

- Coupon security:

    - Use database locking to prevent concurrent redemption

    - Track used coupons; validate not reused

    - Random coupon IDs \(16\+ chars\); validate ownership

- Integer overflow: Set upper limits \(boundaries: 1,073,741,824 and 2,147,483,647\)

- Decimal handling: Use BigDecimal; prevent rounding errors and decimal quantities

- Trial abuse: Track by email/phone/payment method; prevent reset via re\-registration

- Withdrawal races: Use row\-level locking \(SELECT FOR UPDATE\) to prevent concurrent withdrawals

### 2\.10 Exception Handling and Log Auditing \(Items 64\-69\)

Overview: Secure error handling and comprehensive logging without exposing sensitive information\.

Exception Handling:

- Catch specifically: Use precise exception types; never catch and ignore

- Generic user errors: Return "An error occurred" \- never expose stack traces, system details, credentials, or debug info

- Custom error pages: Replace default server error pages with generic messages

Logging Security:

- Never log: Passwords, keys, secrets, authentication tokens in ANY form

- Mask sensitive data: Log PII only after masking/encryption \(credit cards, SSNs, etc\.\)

- Filter log inputs: Prevent log injection via newlines \(`\r\n`\) or malicious code \(XSS, trojans\)

- Retention: Keep network logs for 6\+ months \(per Cybersecurity Law Article 21\)

### 2\.11 Coding Standards \(Items 70\-78\)

Overview: General secure coding practices to prevent common vulnerabilities\.

Requirements:

- Delete obsolete/redundant code and dead branches promptly

- No hardcoded credentials; use environment variables or secure config files

- Prohibit default/weak keys \(shiro, nacos, apisix defaults\); use 32\+ char random keys

- Don't make dangerous methods public \(e\.g\., database deletion methods should be private\)

- Follow correct operation order: validate → authorize → execute \(don't process data before checking permissions\)
